# Стаканы Binance + Aster и кросс-биржевой сигнал

Сервис держит два независимых L2-стакана ETHUSDT (Binance USD-M futures и Aster futures),
публикует из них согласованные снимки и раз в секунду выдаёт решение `HOLD` / `LONG_BIAS` /
`SHORT_BIAS` с обоснованием в числах обеих книг.

## Запуск

```bash
cargo run --release                      # ETHUSDT, параметры по умолчанию
cargo test                               # юнит-тесты: разбор чисел, стакан, синхронизация, сигнал, backoff
cargo run --release -- --help            # все параметры
RUST_LOG=info,ob_signals=debug cargo run --release   # плюс все входы сигнала и детали синхронизации
```

Полезные режимы для проверки:

```bash
# Раз в 10 с сравнивать опубликованный стакан со свежим REST-снимком
cargo run --release -- --verify-every-secs 10

# Внесение сбоев (только в один фид, второй работает нормально)
cargo run --release -- --fault-venue aster --fault-drop-every 100            # потеря кадра => дыра => ресинк
cargo run --release -- --fault-venue binance --fault-garbage-every 60        # битый кадр
cargo run --release -- --fault-venue aster --fault-mute-after-secs 8         # "тихое" соединение => watchdog => reconnect

# Пониженные пороги, чтобы увидеть смену решений
cargo run --release -- --enter-bps 0.5 --exit-bps 0.2 --signal-interval-ms 500
```

## Рынок и источники данных

Выбраны **USD-M futures на обеих площадках**. Публичный API Aster futures повторяет протокол
Binance USD-M (те же поля `U`, `u`, `pu`, тот же формат snapshot), поэтому один синхронизатор
обслуживает обе площадки, а сигнал сравнивает perp с perp.

| | Binance USD-M | Aster futures |
|---|---|---|
| WebSocket | `wss://fstream.binance.com/ws/ethusdt@depth@100ms` | `wss://fstream.asterdex.com/ws/ethusdt@depth@100ms` |
| Поток | `ethusdt@depth@100ms` (diff depth) | `ethusdt@depth@100ms` (diff depth) |
| REST snapshot | `https://fapi.binance.com/fapi/v1/depth?symbol=ETHUSDT&limit=1000` | `https://fapi.asterdex.com/fapi/v1/depth?symbol=ETHUSDT&limit=1000` |

Символ задаётся флагом `--symbol`.

## Архитектура

```text
Binance WS --> [задача фида Binance] --ArcSwap--> BookView binance --+
                (владеет полным стаканом)                            |
                                                                     +--> движок сигнала (раз в 1 с)
                                                                     |
Aster WS ----> [задача фида Aster] ----ArcSwap--> BookView aster ----+--> строка здоровья (раз в 10 с)
                (владеет полным стаканом)

REST snapshot: отдельная задача на каждый запрос, ответ приходит в задачу фида через канал
```

- **Задача фида** (`feed.rs`) - одна на площадку, работает под супервизором. Она читает WS,
  разбирает кадр, применяет его к стакану и публикует снимок. Полный стакан - её локальная
  переменная без `Arc`, без мьютекса и без доступа извне.
- **`BookView`** (`view.rs`) - неизменяемый снимок: верхние 20 уровней на сторону, статус фида,
  `last_update_id`, время биржи, задержка относительно биржи, время публикации и счётчики.
- **Движок сигнала** (`signal.rs`) читает только `BookView` и никогда не трогает WS или полный
  стакан.
- **Строка здоровья** (`status.rs`) читает те же снимки, что и сигнал.

## Хранение: кто пишет, кто читает

**Кто пишет.** В каждый стакан пишет ровно один писатель - задача своего фида. Других писателей
нет, поэтому синхронизация на самом стакане не нужна: `BTreeMap` обновляется как обычная
локальная переменная.

**Кто читает.** Читатели (сигнал, строка здоровья, сверка с REST) видят не стакан, а
опубликованный `Arc<BookView>` в `ArcSwap`. После каждого применённого обновления писатель
собирает новый снимок и атомарно подменяет указатель (`store`). Читатель делает `load` без
блокировок.

**Что видит читатель при гонке с писателем.** Либо предыдущий снимок целиком, либо новый целиком.
Наполовину обновлённой книги не бывает: снимок неизменяем, а подмена указателя атомарна. Если
читатель держит старый снимок, пока писатель публикует новый, старый живёт до последнего `drop`.
Писатель никогда не ждёт читателя, а читатель - писателя.

Почему не `Mutex` или `RwLock` вокруг стакана. Лок на горячем пути связывает писателя с
читателями: долгое чтение (например, сборка top-N или логирование под локом) задерживает
применение обновлений. Вариант "один лок на оба стакана" к тому же связывает фиды между собой.
С `ArcSwap` писатель ни от кого не зависит. Цена - сборка небольшого снимка на каждое обновление
(см. "Горячий путь").

**Согласованность двух книг.** Снимки двух площадок независимы и сделаны в разные моменты. Сигнал
это учитывает: сравнивает время биржи у двух снимков (`skew`) и не принимает решение, если книги
описывают моменты, разнесённые больше чем на 500 мс.

**Что происходит при дыре или ресинке на одном фиде, пока второй жив.** Задача этого фида сразу
публикует снимок со статусом `resyncing` и пустыми уровнями. Со следующего такта сигнал выдаёт
`HOLD` с причиной вида `no signal: aster is resyncing`. Второй фид живёт в своей задаче и
ничего не делит с первым, поэтому он не замечает происходящего. После восстановления
(обычно около 0.5 с) статус снова `live`, и сигнал возвращается к расчёту. Пример из прогона
с `--fault-venue aster --fault-drop-every 100`:

```text
WARN  book out of sync, resyncing on the same connection venue="aster" error=sequence gap: expected pu=624656904415, got pu=624656907668 ...
INFO  feed status venue="aster" from=live to=resyncing
INFO  no signal: aster is resyncing bias=HOLD
INFO  feed status venue="aster" from=resyncing to=live reason="book synced"
INFO  feed health venue="binance" status=live ... connects=1 resyncs=0
```

## Синхронизация стакана

Реализована по документации Binance "How to manage a local order book correctly" для USD-M.
Модуль `sync.rs` не выполняет ввода-вывода и покрыт юнит-тестами.

1. После подключения WS diff-события складываются в буфер. Буфер ограничен 10 000 событий,
   переполнение считается ошибкой.
2. После первого буферизованного события в отдельной задаче запрашивается REST snapshot
   (`limit=1000`). Чтение WS в это время не останавливается.
3. События с `u < lastUpdateId` отбрасываются. Если первое оставшееся событие начинается позже
   snapshot (`U > lastUpdateId`), snapshot устарел и запрашивается заново (до 3 попыток).
4. Первое применяемое событие должно удовлетворять условию `U <= lastUpdateId <= u`.
5. Каждое следующее событие должно иметь `pu == u` предыдущего. Иначе это дыра.
6. Объём абсолютный, нулевой объём удаляет уровень.
7. После каждого применения проверяется, что стакан не пересечён (лучший bid < лучшего ask).

При дыре или пересечённом стакане книга сбрасывается и пересинхронизируется **по тому же
соединению**: новый буфер и новый snapshot. Ответы на snapshot, запрошенные до сброса, помечены
номером поколения и игнорируются.

Цены и объёмы хранятся в фиксированной точке (`i64`, масштаб 10^8) и разбираются прямо из строк
биржи, без `f64`. Ключи стакана точные и полностью упорядоченные. `f64` используется только в
арифметике сигнала.

## Горячий путь

Горячим путём считается отрезок от получения текстового WS-кадра до публикации нового снимка:

- разбор JSON через `serde` в типизированную структуру; цены и объёмы разбираются из `&str`
  сразу в `Fixed`, без промежуточных `String` и `serde_json::Value`;
- применение уровней к `BTreeMap`, проверка последовательности и пересечения;
- сборка `BookView` (20 + 20 уровней) и `ArcSwap::store`.

С горячего пути вынесено:

- **REST snapshot** - в отдельную задачу, чтобы чтение WS не останавливалось.
- **Сигнал** - в отдельную задачу по таймеру; он читает только снимки.
- **Логирование** - на каждый кадр ничего не логируется. В лог пишутся только смены статуса,
  ошибки и периодические строки.
- **Расчёт статистики** - в строку здоровья. Задача фида только увеличивает счётчики.

Время горячего пути измеряется и выводится в строке здоровья (`hot_path_avg_us`,
`hot_path_max_us`). Release-сборка, ноутбук на macOS, ETHUSDT, примерно 8-10 событий в секунду
на фид:

| Площадка | Среднее | Максимум за ~1 мин |
|---|---|---|
| Binance | 56-88 мкс | 461 мкс |
| Aster | 33-37 мкс | 212 мкс |

Это на два порядка меньше интервала между кадрами (100 мс).

### Как проводились замеры

**Время горячего пути** (`hot_path_avg_us`, `hot_path_max_us`):

- Начало: `Instant::now()` сразу после того, как `ws.next()` вернул текстовый кадр, до разбора
  JSON (`feed.rs`, ветка чтения WS).
- Конец: сразу после `ArcSwap::store` нового снимка. Замер записывается только для кадров,
  которые изменили книгу в статусе `live`. Буферизованные до snapshot, пропущенные и битые
  кадры не учитываются, применение самого snapshot тоже.
- `Instant` монотонный, сам замер стоит десятки наносекунд.
- Задача фида копит сумму, количество и максимум с момента запуска процесса (`FeedStats`),
  строка здоровья раз в 10 с печатает среднее (сумма / количество) и максимум. В таблице выше
  "среднее" - диапазон значений `hot_path_avg_us` в строках здоровья за несколько прогонов
  по ~1 минуте, "максимум" - наибольший `hot_path_max_us`.
- Не входит в замер: время в ядре ОС и в буфере сокета, расшифровка TLS, сборка WS-кадра и
  проверка UTF-8 в `tungstenite`, ожидание пробуждения задачи. То есть это время обработки
  кадра нашим кодом, а не полная задержка от сетевой карты.
- Условия: `cargo run --release`, ноутбук на macOS с обычной фоновой нагрузкой, ETHUSDT,
  оба фида одновременно. В debug-сборке значения в несколько раз выше.

**Задержка относительно биржи** (`exchange_lag_ms` в строке здоровья, `lag` во входах сигнала):
локальные часы (`SystemTime`, мс) в момент публикации снимка минус время события `E` из
последнего применённого события. Включает сетевую доставку и нашу обработку, а также смещение
локальных часов относительно часов биржи, которое никак не корректируется. Поэтому иногда
бывают небольшие отрицательные значения (до -8 мс в наших прогонах). Точность - 1 мс.

**Сверка стакана с REST** (`--verify-every-secs`): раз в N секунд запрашивается REST snapshot
с `limit=20`, и верхние 10 уровней каждой стороны сравниваются с опубликованным снимком на
точное совпадение пары (цена, объём). Снимок и REST-ответ сделаны в разные моменты, поэтому
полное совпадение не ожидается. Признак проблемы - систематически почти нулевое совпадение.

**Ограничения.** Есть только среднее и максимум, без перцентилей (p50/p99). Для них нужна
гистограмма (например, `hdrhistogram`). Максимум за всё время работы включает редкие задержки
планировщика ОС на ноутбуке.

**Как один фид не делает второй "молча мёртвым".** У каждого фида своя задача на
многопоточном рантайме tokio. Общего изменяемого состояния у фидов нет: ни общих локов, ни
общего стакана. Тормозящий или зависший фид обнаруживается своим watchdog и отражается в своём
статусе, на втором фиде это не сказывается.

## Отказоустойчивость

Проблемы разделены на два уровня: проблема стакана чинится по тому же соединению, проблема
соединения ведёт к переподключению.

| Что случилось | Реакция | Статус |
|---|---|---|
| Дыра в последовательности (`pu` != предыдущему `u`) | Ресинк по тому же соединению: новый буфер и snapshot | `resyncing` -> `live` |
| Первое событие после snapshot не стыкуется с ним, пересечённый стакан, переполнение буфера | То же | `resyncing` -> `live` |
| Snapshot старше буфера | Повторный запрос snapshot, до 3 попыток | `syncing` |
| REST snapshot не ответил | Повтор через 1 с, затем через 2 с, затем переподключение | `syncing` -> `disconnected` |
| Битый кадр (не разбирается JSON) | Кадр пропускается, растёт `bad_frames`; 20 подряд - переподключение | без изменений |
| 5 с без валидных событий стакана (watchdog; ping-кадры и мусор не считаются) | Переподключение | `disconnected` |
| Сервер закрыл соединение (в том числе плановый разрыв Binance раз в 24 ч), ошибка чтения | Переподключение | `disconnected` |
| Подключение не удалось за 5 с (нет сети, DNS, TLS) | Переподключение | `disconnected` |
| 3 ресинка подряд не дошли до `live` | Переподключение: вероятно, проблема в соединении | `disconnected` |
| Задача фида упала с паникой | Супервизор публикует `disconnected` и запускает задачу заново | `disconnected` |

**Backoff переподключения.** Пауза удваивается от 0.5 с до 30 с, фактическое значение
выбирается случайно из диапазона [половина, полная], чтобы фиды не переподключались синхронно.
Если сессия продержалась в `live` не меньше 30 с, пауза сбрасывается к начальной. На ping
сервера отвечает `tungstenite`.

### Наблюдаемость

- **Каждая смена статуса** фида пишется в лог с причиной (`feed status from=... to=... reason=...`).
- **Строка здоровья** по каждому фиду раз в 10 с: статус и как долго он держится, `stale`
  (фид в `live`, но снимок старше 3 с), события в секунду, возраст снимка, задержка относительно
  биржи, время горячего пути, число подключений, ресинков и битых кадров.
- **Решение сигнала** пишется при каждой смене и раз в 5 с, если не менялось.

### Проверенные сценарии

| Сценарий | Результат |
|---|---|
| Потеря каждого 100-го кадра Aster | Ресинк примерно раз в 11 с, восстановление за ~0.5 с без переподключения; у Binance 0 ресинков и 1 подключение |
| Aster замолкает через 8 с, watchdog 3 с | Watchdog, переподключение с паузами 495 -> 691 -> 1053 мс; Binance всё время `live` |
| Испорченный кадр Binance раз в 60 кадров | Кадр пропущен, `bad_frames` растёт, потерянное событие даёт ресинк |
| Отключение сети на 15-20 с | Сигнал `HOLD` (stale) через 3 с, watchdog через 5 с, попытки подключения по 5 с с растущими паузами; после возврата сети оба фида снова `live` через 1-3 с |
| Сверка с REST (`--verify-every-secs`) | Aster 9-10 из 10 уровней, Binance 3-9 из 10 (REST-ответ новее снимка на несколько тысяч обновлений); дрейфа книги нет |

## Сигнал

**Идея.** Binance - опорный рынок: глубже и быстрее. Сигнал выдаёт bias для бессрочного
контракта Aster. Если mid цена Aster заметно ниже mid цены Binance, ожидаем, что Aster
подтянется (`LONG_BIAS`). Если заметно выше - что опустится (`SHORT_BIAS`). Прибыльность не
оценивалась.

```text
deviation_bps = (mid_aster - mid_binance) / mid_binance * 10^4
deviation <= -порог -> LONG_BIAS,   deviation >= +порог -> SHORT_BIAS,   иначе HOLD
```

**Гистерезис.** Вход в bias при |deviation| >= 1.5 б.п. (`--enter-bps`), удержание, пока
|deviation| >= 0.5 б.п. (`--exit-bps`). Без этого решение переключалось бы на каждом тике, когда
отклонение колеблется около порога. Переход из LONG в SHORT тоже требует порога входа.

**Учёт независимости фидов.** Каждое условие ниже даёт `HOLD`, причина пишется в лог:

| Проверка | Порог | Зачем |
|---|---|---|
| Статус фида не `live` | - | Книги нет или она пересобирается |
| Снимок не обновлялся | 3 с (`--stale-ms`) | Фид замолчал, а watchdog ещё не сработал |
| Отставание от биржи (локальные часы - `E`) | 1000 мс (`--max-lag-ms`) | Кадры приходят, но с устаревшими данными. Такое было вживую: у Binance 4.5 с при маленьком локальном возрасте снимка |
| Расхождение книг по времени биржи | 500 мс (`--max-skew-ms`) | Книги описывают слишком разные моменты, сравнивать их некорректно |

Пример строки решения:

```text
signal changed: deviation=-1.62bps | binance mid=2319.125 | aster mid=2318.750 bias=LONG_BIAS from=Some(Hold)
```

## Компромиссы и что бы я сделал иначе в продакшене

- **Аллокации на каждое событие.** Разбор события создаёт два `Vec` уровней, публикация - два
  `Vec` по 20 уровней и `Arc`. При ~10 событиях в секунду это пренебрежимо мало (см. замеры).
  При тысячах событий в секунду я бы переиспользовал буферы разбора, публиковал снимки не чаще
  N раз в секунду или перешёл на seqlock с фиксированным массивом уровней.
- **`BTreeMap` для стакана.** Это O(log n) на уровень, просто и надёжно. Для HFT лучше
  массив по тикам вокруг текущей цены.
- **Размер стакана не ограничен.** После snapshot в книгу попадают и дальние уровни, если по ним
  приходят изменения. Объём ограничен реальной глубиной стакана биржи; при долгой работе я бы
  периодически обрезал уровни дальше N от лучшей цены.
- **Задержка относительно биржи включает смещение локальных часов** (бывают отрицательные
  значения в единицы миллисекунд). Для точных замеров нужна синхронизация времени или оценка
  смещения по REST `serverTime`.
- **Низкая задержка: что делать и в каком порядке.** Сейчас задержка определяется сетью
  (5-40 мс от биржи до нас), а не обработкой (33-88 мкс на кадр). Поэтому оптимизации ниже
  не сделаны: без них сервис медленнее меньше чем на 1%. Если задержка станет важна, порядок
  такой:
  1. Разместить сервис рядом с биржей. Это выигрыш в миллисекундах.
  2. Выделенный поток ОС на каждый фид вместо задачи tokio, с привязкой к изолированному ядру
     (`core_affinity`, `isolcpus`). Это меньше джиттера: нет переключений контекста и
     переездов между ядрами.
  3. Разделить чтение сети и сборку стакана на два потока со SPSC-очередью на кольцевом буфере
     (crossbeam `ArrayQueue`) между ними, чтобы разбор кадра не задерживал чтение
     сокета. Сейчас на горячем пути очереди нет вовсе, а для передачи состояния сигналу очередь
     не подходит: ему нужно последнее состояние книги, а не каждое обновление, поэтому там
     `ArcSwap`.
  4. Обход ядра ОС при приёме пакетов (DPDK, AF_XDP). Это единицы и
     десятки микросекунд, но нужны специальные сетевые карты, свой сервер и TCP + TLS в
     пространстве пользователя.
- **Метрики только в логах.** В продакшене - Prometheus (гистограммы горячего пути и задержки,
  счётчики ресинков и переподключений) и health-эндпоинт.
- **Ресинки без отдельного backoff.** Частые ресинки ограничены лимитом "3 подряд, затем
  переподключение с backoff", но отдельного учёта веса REST-запросов Binance нет.
- **Сигнал намеренно простой.** Возможные улучшения:
  - microprice вместо mid (на ETHUSDT со спредом в один тик почти ничего не даёт);
  - вычет половины спреда Aster как стоимости входа;
  - фильтр по дисбалансу объёмов в стакане Binance;
  - вычитание скользящего среднего отклонения. Вживую Aster часто держится дороже Binance на
    0.5-0.6 б.п., и это скорее постоянная премия между площадками, чем временное расхождение.

## Структура кода

| Файл | Что внутри |
|---|---|
| `main.rs` | CLI, запуск задач, цикл сигнала |
| `feed.rs` | Задача фида: супервизор, переподключение, сессия WS, ресинк, публикация снимков |
| `sync.rs` | Синхронизация snapshot + diff (без ввода-вывода, с тестами) |
| `book.rs` | L2-стакан на `BTreeMap` |
| `fixed.rs` | Числа в фиксированной точке и их разбор из строк |
| `view.rs` | `BookView`, статусы и счётчики фида, ячейка `ArcSwap` |
| `signal.rs` | Движок сигнала (с тестами) |
| `status.rs` | Периодическая строка здоровья |
| `backoff.rs` | Экспоненциальный backoff со случайным разбросом |
| `faults.rs` | Внесение сбоев для проверки восстановления |
| `verify.rs` | Сверка опубликованного стакана с REST-снимком |
| `venue.rs` | URL и конфигурация площадок |
